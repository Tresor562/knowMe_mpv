# KMD-359 — Canonical PNPM lockfile and frozen CI installs

## Status

Active until the exact final PR head passes the canonical CI and merge gates.

## Goal

Close the remaining JavaScript dependency reproducibility gap left after KMD-358 by committing a real PNPM-generated `pnpm-lock.yaml` and requiring canonical CI installs to honor it without dependency re-resolution.

## Implementation

- `pnpm-lock.yaml` is generated by the repository-pinned `pnpm@10.13.1` on GitHub-hosted Ubuntu/Node 22.23.2.
- The one-time write-capable bootstrap workflow used only to generate the lockfile is removed before final validation and must never reach `main`.
- Canonical CI now runs `pnpm install --frozen-lockfile`.
- `scripts/pnpm-lockfile-preflight.test.mjs` verifies that the lockfile exists, is non-empty, uses lockfile format 9.0, retains the exact repository PNPM version, and that canonical CI cannot silently restore `--frozen-lockfile=false`.

## Security and supply-chain boundary

KMD-359 does not weaken the existing immutable GitHub Action pins, exact CI Node version, exact direct dependency pins, unsuppressed production high/critical audit, immutable PostgreSQL image, or immutable runtime Node image requirements.

The temporary generator used only the already audited immutable checkout, PNPM setup and Node setup action SHAs. It was restricted to same-repository pull requests and removed immediately after `pnpm-lock.yaml` was generated and committed.

## Validation required before merge

On the exact final head:

1. lockfile/supply-chain/package pinning preflights pass;
2. `pnpm install --frozen-lockfile` succeeds without changing the lockfile;
3. `pnpm audit --prod --audit-level=high` passes without advisory suppression;
4. Prisma generation, migration deploy and schema drift checks pass;
5. complete monorepo build and tests pass;
6. Web Playwright E2E passes;
7. PostgreSQL-backed API E2E passes;
8. no blocking review or unresolved review thread remains.

## Migration

No database or user-data migration is introduced.

The repository dependency-resolution state changes from implicit registry resolution to an explicit committed lockfile. This is a source/release engineering change only.

## Rollback

If the generated lockfile proves invalid, revert KMD-359 as one delivery and return to the preceding KMD-358 state while diagnosing the resolver issue. Do not hand-edit the lockfile and do not keep a partially valid lockfile with non-frozen CI.

## Proof boundaries

KMD-359 does not claim completion of:

- real supported-device Web/iOS/Android validation;
- legal/privacy review;
- production backup/restore execution;
- production monitoring or alert delivery;
- production deployment;
- App Store or Google Play submission/publication;
- canonical `main` branch protection configuration.

Those require independent real-world evidence.
